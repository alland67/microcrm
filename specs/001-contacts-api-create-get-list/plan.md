# 001: Contacts API: create, get by id, list (paging + search): Technical plan

**Status:** Planned
**Spec:** ./spec.md
**Approved:** 2026-10-01
**ADRs:** ADR-0003 (case-insensitive text in SQLite), ADR-0004 (validation and error pipeline), ADR-0005 (integration test database)

## Approach
This is the first feature on a freshly bootstrapped minimal-API host. It adds a `Contacts` feature folder (`MapGroup("/api/contacts")`), an EF Core + SQLite `AppDbContext` with migrations, and a ProblemDetails error pipeline that later specs inherit unchanged. The template's `weatherforecast` sample is removed in T-01.

Three design choices shape everything else:

1. **The database enforces the hard rules.** Email uniqueness is a unique index on a `NOCASE`-collated `Email` column. There's no application pre-check, and the constraint violation maps to 409. Case-insensitive sort uses the same collation, and search uses escaped `LIKE` (ADR-0003).
2. **Validation and parsing are pure functions called from the handlers, not framework binding.** That's the only way to get trim-aware lengths (AC-009), one response listing every error (AC-014), and named errors for non-integer query values (AC-028). All error responses come from a single, environment-independent ProblemDetails pipeline (ADR-0004).
3. **Integration tests run against a real, migrated, named in-memory SQLite database per test class**, through real HTTP. That makes concurrency (AC-016) and persistence across connections (AC-039) testable without flakiness from a shared connection (ADR-0005).

Queries stay in the endpoint handlers (conventions: "keep queries in handlers until duplication justifies extraction"). Only the pure rules (contact input normalization/validation, list query parsing, LIKE escaping) go into separate types, because they're unit-tested.

Migrations are applied at API startup (`Database.MigrateAsync()` after `Build()`, before `Run()`). For a single-user local app this removes a manual step, and it gives the test host its schema. Revisit before any deployment (roadmap "later").

## Interfaces & data

### HTTP contract
```text
POST /api/contacts
  Request  (application/json), all members optional at the JSON level, unknown members (id, createdAt, ...) ignored:
    { "firstName": string?, "lastName": string?, "email": string?, "phone": string?, "company": string?, "notes": string? }
  201 Created   Location: /api/contacts/{id}    Body: Contact
  400           application/problem+json, validation: { type, title, status, errors: { firstName?: [..], lastName?: [..], email?: [..], phone?: [..], company?: [..], notes?: [..] } }
  400           application/problem+json (malformed/empty JSON, wrong JSON type; no errors dictionary required)
  409           application/problem+json (duplicate email)

GET /api/contacts/{id:guid}
  200 Body: Contact
  404 application/problem+json (unknown GUID, and also non-GUID id because no route matches)

GET /api/contacts?page=&pageSize=&search=
  200 Body: { "items": Contact[], "page": int, "pageSize": int, "totalCount": int }
  400 application/problem+json, validation: errors keyed "page" | "pageSize" | "search"

Contact (JSON, camelCase, nulls always present):
  { "id": "<guid v7>", "firstName": string, "lastName": string|null, "email": string|null,
    "phone": string|null, "company": string|null, "notes": string|null,
    "createdAt": "<ISO-8601, offset +00:00>", "updatedAt": "<ISO-8601, offset +00:00>" }

Any unexpected exception -> 500 application/problem+json { type, title, status[, traceId] }, with no exception message, type name, or stack trace.
```

### Schema (SQLite, after all three migrations)
```sql
CREATE TABLE "Contacts" (
  "Id"        TEXT NOT NULL CONSTRAINT "PK_Contacts" PRIMARY KEY,   -- Guid (EF stores as upper-case text)
  "FirstName" TEXT COLLATE NOCASE NOT NULL,                          -- max 100 (enforced in ContactInput, not in the schema)
  "LastName"  TEXT COLLATE NOCASE NULL,                              -- max 100 (ContactInput)
  "Email"     TEXT COLLATE NOCASE NULL,                              -- max 254
  "Phone"     TEXT NULL,                                             -- max 50
  "Company"   TEXT NULL,                                             -- max 200
  "Notes"     TEXT NULL,                                             -- max 4000
  "CreatedAt" TEXT NOT NULL,                                         -- DateTimeOffset, EF text format, 7 fractional digits
  "UpdatedAt" TEXT NOT NULL
);
CREATE UNIQUE INDEX "IX_Contacts_Email" ON "Contacts" ("Email");     -- NOCASE inherited from column; multiple NULLs allowed
```

## Design points (resolved)

### 1. Email uniqueness enforced by the database (AC-011, AC-013, AC-016)
- **Choice:** `NOCASE` collation on `Email` + unique index `IX_Contacts_Email` (ADR-0003). A normalized shadow column was rejected. NOCASE folds exactly ASCII A–Z (Q1), and the same collation already serves sort.
- **Flow:** `ContactInput.Parse` trims (and nulls empty values) → build `Contact` → `SaveChangesAsync`. On `DbUpdateException` where `SqliteErrors.IsUniqueConstraintViolation` is true → `TypedResults.Problem(statusCode: 409, title: "A contact with this email already exists.")`. There's **no pre-check query**, so the sequential (AC-011) and concurrent (AC-016) cases take one code path. Every other `DbUpdateException` is re-thrown and becomes a 500 through the exception handler. Nothing is swallowed.
- **The problem detail must not echo the email** (NFR-004 spirit; ProblemDetails can end up in logs).
- **Testing concurrency deterministically:** the race outcome can't be scheduled, so the tests make assertions that are **true for every interleaving**, and they prove the mechanism separately:
  1. *Schema-level proof (deterministic):* the test opens its own connection to the test database and inserts two rows directly whose emails differ only in case. The second insert must fail with `SqliteException` (extended code 2067). This proves the database, not the app, is the arbiter, independent of timing.
  2. *Sequential proof (deterministic):* AC-011 through HTTP. Because there's no pre-check, this exercises exactly the constraint→409 path that a lost race takes.
  3. *Concurrent smoke (interleaving-invariant):* release N = 10 `POST`s with the same email in different casings at once (`Task.WhenAll`, after a shared `TaskCompletionSource`/`Barrier` start signal). Assert exactly one 201, nine 409s with `application/problem+json`, **zero 5xx**, and exactly one matching row (counted through a separate connection). Whatever the scheduling, these assertions hold, so the test isn't flaky. It fails if writes aren't safely serialized or a race path produces a 500.
- **Shared-connection caveat:** a single shared `SqliteConnection` does **not** serialize writes safely. Microsoft.Data.Sqlite connections aren't thread-safe, and two requests on one connection collide (for example "nested transactions" errors that surface as 500). The conventions' single `:memory:` connection would make test 3 flaky for reasons unrelated to the product. ADR-0005 therefore uses a **named shared-cache in-memory database** with a connection per `DbContext`. SQLite serializes writers, and Microsoft.Data.Sqlite retries busy/locked errors until the command timeout (default 30 s).

### 2. Case-insensitive sort and search; nulls last; literal wildcards (AC-022, AC-023, AC-029, AC-033)
- **Sort:** `OrderBy(c => c.LastName == null).ThenBy(c => c.LastName).ThenBy(c => c.FirstName).ThenBy(c => c.Id)`, which EF translates to `ORDER BY "LastName" IS NULL, "LastName", "FirstName", "Id"`. ORDER BY on a column uses the column's collation, so `NOCASE` on `FirstName`/`LastName` (migration in T-12) makes name comparison case-insensitive. `Id` compares as BINARY text (ordinal on the upper-case canonical GUID string). Tests derive the expected tie-break order with an ordinal comparison of the id strings, ignoring case. That's equivalent, because hex digits sort the same way in either case.
- **Search:** for a non-null trimmed term, `pattern = LikePattern.Contains(term)` and filter `EF.Functions.Like(c.FirstName, pattern, "\\") || EF.Functions.Like(c.LastName!, pattern, "\\") || EF.Functions.Like(c.Email!, pattern, "\\")`. SQLite `LIKE` folds ASCII case by default. Escaping order is `\` first, then `%` and `_`. Don't use `string.Contains`, because the provider can translate it to case-sensitive `instr()`.
- **Pipeline order** (AC-036): filter → `CountAsync` (totalCount) → order → `Skip`/`Take`. Two queries, no transaction; the spec assumes no concurrent changes while paging.
- Recorded in **ADR-0003**.

### 3. Non-GUID ids, 404s, and every error as ProblemDetails; safe 500s (AC-018, AC-019, AC-037, AC-038)
- `GET /api/contacts/not-a-guid` doesn't match `{id:guid}`, and no other route matches, so the pipeline ends with an empty 404. `UseStatusCodePages()` with `AddProblemDetails()` registered writes `application/problem+json` with the default `type`/`title`/`status` for any empty-body 4xx/5xx. The same mechanism covers `TypedResults.NotFound()` (AC-018), binding 400s (AC-015), and 415s.
- `UseExceptionHandler()` (no path, using `IProblemDetailsService`) is registered **first and in every environment**. Development automatically adds the developer exception page as the outermost middleware, but the explicit handler sits inside it and handles the exception first. The 500 body is `{type,title,status,traceId}` only. AC-038 is tested **in Development** (the factory's environment), which is the worst case.
- **Order in Program.cs:** `UseExceptionHandler()` → `UseStatusCodePages()` → (OpenAPI in Development) → endpoints. `UseHttpsRedirection()` is kept only if it doesn't break the HTTP-only dev proxy; the implementer may drop it (no AC depends on it).
- Recorded in **ADR-0004**.

### 4. Binding failures as 400 ProblemDetails (AC-015, AC-028)
- **Query (AC-028):** `page`, `pageSize`, and `search` are bound as `string?`, so binding can't fail. `ListQuery.Parse` uses `int.TryParse(value, NumberStyles.None, CultureInfo.InvariantCulture, ...)`. `"abc"`, `"1.5"`, `""`, `"-1"`, `"0"`, `"101"`, and values beyond `int` range each produce `errors["page"]` or `errors["pageSize"]`. The handler returns `TypedResults.ValidationProblem(errors)`, a 400 `application/problem+json` with an `errors` dictionary. All offending parameters are reported together. `(page - 1) * pageSize` is computed in `long`. If it exceeds `int.MaxValue`, the result is an empty page (still 200, AC-026).
- **Body (AC-015):** `RouteHandlerOptions.ThrowOnBadRequest = false` (all environments). Malformed JSON, an empty body, a JSON `null` body, or a wrong JSON type (for example `"firstName": 123`) makes the framework set 400 without a body. Status code pages then writes ProblemDetails. AC-015 requires ProblemDetails but no `errors` dictionary, and the plan doesn't add one. Missing `firstName` isn't a binding failure, because every request property is nullable. It's a validation error with `errors.firstName` (AC-007).
- **Create validation (AC-007..AC-010, AC-014):** `ContactInput.Parse` collects **all** errors in one pass and returns them keyed by camelCase field name.
- Recorded in **ADR-0004**.

## Risks & mitigations
- **Shared-cache locking flakiness in AC-016.** Mitigation: interleaving-invariant assertions; Microsoft.Data.Sqlite's built-in busy/locked retry; fallback to a temporary file DB per factory (ADR-0005, option 3) without production changes.
- **Developer exception page leaking details in Development (AC-038).** Mitigation: explicit `UseExceptionHandler()` in all environments; the test runs in Development.
- **AC-015 behavior differs by environment** (`ThrowOnBadRequest`). Mitigation: set it to `false` explicitly; ADR-0004.
- **`TypedResults.Conflict(...)` writes `application/json`, not problem+json.** Mitigation: use `TypedResults.Problem(statusCode: 409)` (ADR-0004); `ProblemAssert` catches regressions.
- **`string.Contains` translating to case-sensitive `instr()`.** Mitigation: `EF.Functions.Like` with an explicit escape (ADR-0003); mixed-case search tests.
- **Skip overflow** for huge `page`. Mitigation: `ListQuery.TryGetSkip` computes in `long`; unit test + AC-026 test with `int.MaxValue`.
- **"Characters" for max length.** `string.Length` counts UTF-16 code units, so an emoji counts as 2. The plan uses `string.Length`. Q8 resolved at plan approval (2026-10-01): keep `string.Length`. Tests use ASCII.
- **EF error logging on 409.** EF logs failed `SaveChanges` at Error. Without sensitive-data logging, parameter values are not included (NFR-004). Never enable `EnableSensitiveDataLogging`; the NFR-004 guard test catches a regression.
- **Generated migration files vs `dotnet format --verify-no-changes` and warnings-as-errors.** They carry `// <auto-generated />`, so analyzers and format skip them. If not, the implementer adds a targeted `.editorconfig` `generated_code = true` section for `Data/Migrations/**`.
- **Package version drift.** Tests use `Microsoft.AspNetCore.Mvc.Testing` 10.0.12 while the API uses `Microsoft.AspNetCore.OpenApi` 10.0.0. Not blocking; see follow-ups.
- **Tests that pass at RED** (guards). Some ACs are satisfied as a side effect of an earlier or the same task's implementation. tasks.md flags each one explicitly. The test-writer records them as guards in the RED report, and the reviewer confirms each would fail if its behavior regressed.
